# 通用对话数据与 Prompt 工作流

`conversation-data-workflow` 是一套可配置的 Codex Skill：将对话数据提取、业务名单标注、历史分析、测试集构建、单轮/多轮评测及 Prompt 迭代连接起来。每个模块可以独立使用，也可以按任务组合。

适用于外呼、客服、预约回访、售后等业务。产品、国家、语言、分组、名单事件与业务规则由配置决定；OKash M2/M3 是可选示例，不是通用默认。

**本包提供代理执行规范、场景配置与离线检查工具，不是全自动批处理引擎。** Codex 根据规范完成实际任务；`prepare_run.py` 只检查配置和文件前置条件，不执行导出、标注、模型调用或报告生成。

## 1. 模块、原小 Skill 与工作流的关系

下表是能力来源与迁移关系。八个原小 Skill 被整理为七个模块，其中两种导出合并为 `extract` 的两个子功能。

| 原小 Skill | 通用模块 | 保留的核心能力 |
|---|---|---|
| `okash-call-export` | `extract`：calls | 精确项目筛选、录音记录导出、数量与文件完整性核验 |
| `okash-repayment-export` | `extract`：outcomes | 按名单查询标识导出、保留原始结果与时间范围 |
| `okash-repayment-mark` | `annotate` | 客户身份映射、同组全部通话标注、证据与未知项管理 |
| `opay-collection-analysis` | `analyze` | 数据质量、分层指标、完整上下文案例与修改建议 |
| `call-asr-testset` | `testset` | 用户轮次抽样、语义审阅、模拟覆盖与来源追溯 |
| `opay-prompt-evaluation` | `evaluate` | 独立单轮对比、断点恢复、历史输出重评 |
| `opay-multiturn-evaluation` | `multiturn` | 场景角色、多轮历史、停止条件与会话级对比 |
| `opay-prompt-iteration` | `iterate` | 完整候选版本、证据映射、差异与回归用例 |

**当前关系是独立整理，不是动态调用。** 新技能读取自己 `references/` 中的模块规范，不会自动执行原小 Skill，也不要求使用者安装它们。修改原小 Skill 不会自动更新本工作流；修改本地工作流也不会自动推送 GitHub。可兼容复用的旧脚本须先核验格式与参数，不能盲用旧业务默认值。

模块通过文件、hash和清单衔接，而不是仅凭文件名“看起来相同”来判断可复用。

## 2. 模块功能详解

以下每个调用示例都应附上自己的配置文件路径与场景ID。不会因为调用一个模块，就自动执行所有前置模块。

### 2.1 `extract`：原始通话与业务名单提取

**解决什么问题：** 从指定后台取得可以追溯、验证并归档的原始文件，避免选错项目、混入其他组或把不完整下载当作导出成功。

**需要的输入：** 后台访问权限、数据源、时间范围、场景数据目录，以及通话项目完整值或名单查询Token。`extract_kinds` 可选 `calls`、`outcomes`，也可两者都选。

**具体处理：**

1. `calls` 进入外呼底层表，以项目条件与录音地址非空条件共同筛选；导出后检查JSON中的完整项目值，避免`:3`误匹配`:30`。
2. `outcomes` 进入子任务更新记录表，按完整查询Token导出；不擅自推断状态码意味着还款、预约或成交。
3. 核对下载事件、文件稳定性、CSV完整解析及记录数。文件按CSV记录计数，不按文本物理行计数。
4. 保留原文件字节，核验SHA-256；记录查询范围与实际记录覆盖范围，两者不能混为一谈。
5. 大批量可按不重叠时间段拆分；零记录须有成功查询证据，查询失败不能写成零记录。

**交付：** 原始CSV、每组/类型的导出清单、筛选与时间口径、文件hash、行数及异常说明。

**单独调用：**

> 使用 $conversation-data-workflow，按指定配置只执行 extract；extract_kinds 选择 calls，只导出指定项目的通话，不导出名单。

**边界：** 当前适配的是既有Buildstore页面，不是通用数据库采集器。录音地址存在不自动证明真实接通；更新记录属于什么业务名单，需要使用者给出依据。

详见 [提取规范](references/extract.md)。

### 2.2 `annotate`：业务名单匹配与数据标注

**解决什么问题：** 把“客户是否命中目标事件名单”关联到该客户的每条通话，保留可核验的匹配依据。

**需要的输入：** 同场景通话文件、业务名单、事件含义与覆盖窗、字段映射和身份关联方式。事件可以是还款名单、预约名单或其他已确认业务名单。

**具体处理：**

1. 客户ID可靠时按字符串精确关联，保留前导零；`001`与`1`不视为同一客户。
2. 名单有已核实客户电话时直接使用。名单只有任务标识时，通过Token、批次任务ID、子任务ID定位后台详情，在subTaskInfo核实本人电话。
3. 电话按已确认国家及规则规范化，不猜数字、不截尾匹配、不使用联系人或空值匹配。
4. 同组客户的全部通话同步标注；跨组相同ID或号码不能直接借用另一组名单。
5. 映射不完整、身份含糊或号码无效时保留unknown/待核对，不把这些行强制标No。
6. 复跑时追溯旧Yes证据，缩小名单时间窗不能静默把已确认Yes降为No。

**交付：** 标注CSV、身份映射、来源hash、未解决项、客户数与通话数统计。默认另存副本；明确要求原位更新时，先备份、逐值核验，再原子替换。

**单独调用：**

> 使用 $conversation-data-workflow，只执行 annotate，用本地已预约名单按 customer_id 标注全部同组通话，输出列为“预约名单匹配”。

**边界：** Yes表示命中所用名单，No表示未命中；二者都不是“这通电话促成了业务结果”的因果证明。只有Yes/No正式格式时，未知项影响的组暂不发布完整正式结果。

详见 [标注规范](references/annotate.md)。

### 2.3 `analyze`：数据质量、业务指标与对话问题分析

**解决什么问题：** 从已有数据中说明哪些现象可确认、哪些存在缺口，以及下一版Prompt应该优先修改什么。

**需要的输入：** 通话与ASR、实际字段及角色映射。名单和标注可选；缺失时仍可完成数据质量与对话分析，结果匹配率标为不可计算。

**具体处理：**

1. 检查编码、空值、重复、冲突、时间范围和来源；通话去重与客户去重分别定义。
2. 分开计算“匹配客户数/有效客户数”和“匹配通话数/通话数”，说明未知身份、漏标和窗口限制。
3. 根据场景分层：如日期、时长、交互次数；催收场景才采用金额、逾期和减免维度。
4. 结构化字段优先；ASR中的金额、预约时间等仅作为话术提及值，附提取依据与覆盖率。
5. 区分固定开场与动态回复，阅读完整上下文，检查承接、重复追问、障碍处理、事实与权限等表现。
6. 结合脱敏案例形成优先建议，每项写清“证据→问题→具体修改→测试→验收条件”。

**交付：** 每场景独立HTML报告、指标、案例索引、提取/判定规则、数据缺口和Prompt改动建议。

**单独调用：**

> 使用 $conversation-data-workflow，只执行 analyze，分析现有通话的客户诉求和客服承接问题。没有交易数据，不计算真实回款率或通话后转化。

**边界：** 规则命中不是全量人工质检分数；案例抽查不能推断全量发生率；没有真实事件时间和统一观察窗，不计算因果提升或ROI。

详见 [分析规范](references/analyze.md)。

### 2.4 `testset`：真实用户话术与模拟覆盖测试集

**解决什么问题：** 建立可以跨版本复用、有来源证据且覆盖关键场景的离线测试输入。

**需要的输入：** 原始ASR、实际列名与结构、角色标签、真实/模拟数量、随机种子、每通限额，以及模拟场景覆盖要求。

**具体处理：**

1. 识别文本或JSON的实际ASR结构，正确分离用户轮次与客服轮次，不固定假设第K列。
2. 按规范化键去重、固定种子排序，再按每通限额生成候选；保留原始拼写、语言和标点。
3. 逐条语义审阅，保留有意义的短回答和方言，排除严重识别残缺、自动接听或角色混入。
4. 真实数量不足时报告缺口，不改写原话或用模拟话术冒充真实样本。
5. 按本业务政策和语言生成模拟覆盖，与真实数据跨集去重，来源明确分开。
6. 冻结测试集版本与hash；同条件版本对比沿用固定集，不在中途重新抽样。

**交付：** 两列主表`测试话术,测试ID`，以及来源明细、候选、审阅决定、抽样与场景覆盖报告。数量由配置决定，200真实＋100模拟只是一个可选组合。

**单独调用：**

> 使用 $conversation-data-workflow，只执行 testset，抽取150条真实用户回复并追加50条售后模拟话术，每通最多一条；不足真实额度时报告缺口。

**边界：** 经过质量筛选的样本不是原始客户分布的无偏估计。`testset`主要产出单轮输入；多轮需要另外冻结角色、可见前缀和状态，不能把两列CSV直接当完整多轮场景库。

详见 [测试集规范](references/testset.md)。

### 2.5 `evaluate`：单轮版本对比与历史结果重评

**解决什么问题：** 用同一批输入和业务条件，比较不同Prompt的实际输出，并能在修改评分标准时复用历史回复。

**需要的输入：**

- `generate`：固定测试集、指定baseline/candidate、业务夹具及来源、量表与版本、生成参数及接口文档。
- `rejudge`：已有响应归档索引、量表及版本；不要求重新调用模型。历史元数据缺失会限制可比性。

**具体处理：**

1. 冻结Prompt正文和渲染结果、测试集、业务参数、生成设置与量表hash。
2. 每条测试独立构造system＋user上下文，不擅自增加开场、工具或隐藏提示。
3. 调用前发现实际模型；先做小规模响应检查，再按全局并发上限执行。请求和响应逐条落盘，支持断点恢复与有限重试。
4. 对空回复、截断、未知状态及网络错误单独记账，不把HTTP成功当业务有效。
5. 依据同一量表与共同可判定分母分析改善、退步、持平和未知；只复用条件相符的历史基线。
6. `rejudge`仅读取实际历史输出并新增评分批次，保留旧报告。

**交付：** 每场景HTML、逐条评分、按轮次CSV、原请求响应、任务索引、模型/参数与运行清单。

**单独调用：**

> 使用 $conversation-data-workflow，只执行 evaluate，按配置比较V0与V1.2，复用固定测试集。满足可比性条件的旧基线直接复用。

> 使用 $conversation-data-workflow，执行 evaluate 的 rejudge 模式，按新量表重新评价已有归档，不重新生成模型回复。

**边界：** API成功率不是业务效果分；没有逐条语义审阅，不输出全量语义通过率。调整模型、政策或测试集后，不直接把差异归因于Prompt。

详见 [单轮评测规范](references/evaluate.md) 与 [Gateway执行规范](references/gateway.md)。

### 2.6 `multiturn`：角色模拟与多轮对话评测

**解决什么问题：** 检查客服能否在连续交互中记住事实、承接追问、处理障碍、调整方案并合理结束，补充单轮评测看不到的问题。

**需要的输入：** 冻结的场景库、角色事实与可变状态、Prompt版本、共同业务参数、起始方式、重复次数、轮次/时间上限、请求预算及会话级量表。

**具体处理：**

1. 采用相同场景与角色比较版本，可从相同真实前缀分叉（prefix_fork）、从真实触发语派生模拟（scenario_seed），或按明确开场机制新建会话（fresh_start）。
2. 当前通用模块按独立用户/客服system与历史组织模型角色；用户侧不能接收客服系统Prompt、版本名或评分答案。
3. 根据客服实际回复推进用户状态与下一轮；同会话串行，不同会话可以并发，全部模型请求共享全局上限。
4. 校验用户结构化输出、事实与状态变更；无效轨迹单列，不伪造台词继续测试。
5. 按挂断、明确结束标记、轮次/时间限制等停止；达到上限记截断，不强行算成功。
6. 保存逐轮上下文与状态，按case和repeat配对比较，评价理解、记忆、障碍处理、可执行计划、权限与沟通表现。

**交付：** 原始请求响应、完整生成对话、用户状态轨迹、逐轮CSV、会话级评分及独立HTML报告；区分客服缺陷、模拟器偏差、接口错误和证据不足。

**单独调用：**

> 使用 $conversation-data-workflow，只执行 multiturn，使用配置中冻结的场景库对比V0与V2.1，遵守已设定的轮次、重复次数与请求预算。

**与原小Skill的差异：** 原多轮小Skill后来新增了`assistant_direct`（当前代理直接扮演用户）模式。本包不会自动同步该变更；当前通用执行规范仍以模型用户角色为基础。历史接续可以识别这两类来源，但不能把它们混成同条件基线，也不能宣称本包已默认切换为代理直接扮演。

**边界：** 模拟承诺、模拟点击或模拟付款不是真实业务达成。单轮基线不能替代多轮基线；同模型自我模拟的偏差应披露。

详见 [多轮规范](references/multiturn.md)。

### 2.7 `iterate`：证据驱动的完整 Prompt 版本迭代

**解决什么问题：** 将报告发现转成完整、可测试且可追溯的新Prompt，而不是仅给一段零散补丁。

**需要的输入：** 明确的父版本文件及hash、目标版本、同场景报告或评测证据、业务政策，以及必须保留的变量和输出约定。

**具体处理：**

1. 阅读完整父版本和报告，确认报告对应的真实被测版本；不能仅靠修改时间推断。
2. 优先处理证据最强的少数问题，建立“报告/案例→修改位置→期望行为→回归测试”的关系。
3. 修改完整Prompt并移除冲突规则，保留语言、品牌、模板变量大小写及结束标记。
4. 新字段需明确供值方、类型和缺失行为；工具、到账、预约确认等平台能力不能靠Prompt假装具备。
5. 保留全部历史版本，冲突版本另存候选，不覆盖；版本按整数段排序，例如V1.10在V1.9之后。
6. 完成静态检查，生成带预期行为的回归用例；未运行模型回放时标为not_run。

**交付：** 完整TXT、按需要生成且回读一致的RTF、diff、HTML修改说明、版本清单和回归用例。

**单独调用：**

> 使用 $conversation-data-workflow，只执行 iterate，依据指定分析报告和V1.2父版本生成V1.3完整候选，保留变量与业务权限，不启动模型测试。

**边界：** 文件生成不等于模型通过、优于旧版本或已上线；部署与线上实验不在默认范围内。

详见 [迭代规范](references/iterate.md)。

## 3. 组合后可以完成什么

组合不是简单连续调用七个名字，而是把上一步经过验证的产物作为下一步输入，并保留场景、版本、窗口和hash。

### A. 从原始业务数据到新Prompt候选

**流程：** `extract → annotate → analyze → iterate`

**适用：** 已有真实业务名单，想知道现有客服哪里做得不好，并据此改版。

- 提取：拿到同场景通话和结果名单，冻结来源。
- 标注：把名单匹配关联到客户全部通话，说明未知项与窗口差异。
- 分析：分开业务匹配现象与对话质量，定位最有证据的问题。
- 迭代：使用明确父版本，将建议落实为完整候选、diff和回归用例。

**最终交付：** 可追溯原始数据、标注结果、业务与对话报告、新Prompt候选。**此流程没有模型验证阶段**；要验证候选，应再选择evaluate或multiturn。

> 按配置执行 extract、annotate、analyze、iterate；沿用指定父版本，输出待测试候选，不上线。

### B. 用已有本地文件完成业务诊断

**流程：** `annotate → analyze`

**适用：** 通话与名单已经下载，无须再访问后台导出。

客户ID或已验证电话足够时直接本地匹配；只有缺失身份映射才需要按授权读取后台详情。分析阶段引用原标注证据，区分客户与通话分母。

**最终交付：** 标注CSV、身份/未知项证据、分层指标、对话问题报告和修改方向，不生成新Prompt。

> 只使用指定本地文件执行 annotate、analyze；按客户ID关联，不查询后台、不调用模型。

### C. 固定测试集上的单轮迭代

**流程：** `testset → evaluate → iterate`

**适用：** 想在一致输入下对比已有两版Prompt，再按缺陷生成下一版。

- 构建或复用测试集，冻结输入及来源。
- 对照指定baseline与candidate，保存实际输出和逐例评价。
- 根据该批评测中证据充分的缺陷生成下一版候选。

**最终交付：** 测试集、版本对比报告、下一版完整Prompt及回归用例。最后生成的新版本**还没有被前面的评测测试过**，需要新的运行才能验证。

> 执行 testset、evaluate、iterate；已有固定集则复用，对比V0和V1.2，再从明确的V1.2父版本生成V1.3候选。

### D. 多轮行为诊断与迭代

**流程：** `multiturn → iterate`

**适用：** 关注持续追问、记忆、困难处理、协商和结束行为。

先准备/确认多轮场景库与角色，冻结前缀、事实、参数和量表。用相同场景比较版本，再把有逐轮证据的缺陷落实到新Prompt。

**最终交付：** 可回看完整轨迹、会话级对比、模拟器局限、候选Prompt与多轮回归场景。修改角色、用户执行方式或测试库后必须重新建立同条件比较。

> 执行 multiturn、iterate，按冻结角色比较指定版本，把多轮失误对应到新候选中的具体修改。

### E. 不重新生成回复，利用历史结果继续迭代

**流程：** `evaluate(mode=rejudge) → iterate`

**适用：** 已有原始回复，但评分口径改变或旧结论需要复核。

读取历史响应索引，按新量表重新判读并另存评分批次，再结合实际父版本形成候选。缺少历史事实、Prompt或参数的指标保留不可判定，不为了凑齐条件重新编造数据。

**最终交付：** 新评分报告、旧/新判读依据、候选版本与限制说明；不向模型重新发送测试集。

> 使用rejudge重新评价指定历史批次，再执行iterate；保留旧报告，不重新生成回复。

### F. 沿用原目录，从任意阶段接续

**流程：** `历史定位与hash核验 → 所选模块`

**适用：** 以前的小Skill已经产生数据、测试集、Prompt和报告，希望继续使用这些文件。

配置`layout_mode=legacy`、`history`和每场景`outputs`。通过索引找到原件，核验后复用；新结果写回各模块原来的目录体系。已有测试集不重抽，已有成功响应不重新生成，只有真实条件变化才建立新运行。

**最终交付：** 指向原件的可追溯运行清单及新产物，无须搬走全部历史文件。

### 完整循环如何组织

需要“改完再测”时，按独立运行组织：

```text
运行1：原数据 → 标注 → 分析 → 候选V1
运行2：固定测试集 → 对比V0/V1 → 报告
运行3：基于运行2 → 候选V1.1
运行4：同测试集 → 对比指定基线/V1.1
```

每轮明确版本、输入快照和预算，不能把最后新生成的候选称为已经通过上一轮评测。当前检查脚本的`--steps`是有序且不重复的模块列表；重复模块放到新运行，不写`iterate,evaluate,iterate`来隐含无限循环。

## 4. 组合任务的共同规则

| 情况 | 如何处理 |
|---|---|
| 已有合格上游文件 | 按场景、hash和合同复用，不强迫重跑 |
| 一组数据缺失 | 阻塞该组依赖步骤，独立组继续 |
| 名单映射未完成 | 标注保留未知；可继续不依赖业务标签的对话分析 |
| Prompt父版本不明确 | 整理证据与候选列表，不自行按修改时间选版 |
| 某请求超时 | 保存unknown和重试记录，不声明未执行或成功 |
| 测试集、角色、模型或量表变化 | 新建快照/批次，说明可比性变化 |
| 新结果写入共享目录 | 文件名带场景、版本或运行ID，不覆盖旧产物 |

每一步记录输入与输出hash、配置hash、数量、状态、限制。状态区分`complete/partial/blocked/failed/not_run`；配置工具的`ready_for_agent_verification`只代表可进入进一步核验。

## 5. 安装与离线演示

### 环境

- 支持本地Skill的Codex环境。
- Python 3.9或更高版本；配置检查和测试脚本只用标准库。
- Buildstore导出需要使用者自己的登录权限与浏览器工具。
- 模型评测需要既有Gateway访问权限；包内不含账号和密钥。
- RTF提取的现有流程使用macOS `textutil`；其他系统优先提供TXT，或使用经过全文一致性验证的转换工具。

### 安装

解压ZIP，把整个`conversation-data-workflow`文件夹放入本机技能目录：通常是`~/.codex/skills/`；配置了`CODEX_HOME`时使用其下的`skills/`。不要只复制SKILL.md。

```text
conversation-data-workflow/
├── SKILL.md                 代理入口与模块路由
├── README.md                使用说明
├── agents/openai.yaml       展示信息
├── assets/                  通用配置、脱敏业务示例
├── examples/appointment/    虚构预约数据与配置
├── references/              七模块、接口、历史复用规范
└── scripts/                 离线配置检查与测试
```

在新任务中调用`$conversation-data-workflow`；尚未显示时可让Codex读取安装目录的SKILL.md。更新已有安装前先保留自己的场景配置，避免用公开模板覆盖真实配置。

### 验证离线示例

在技能目录执行：

```bash
python3 scripts/prepare_run.py --config examples/appointment/scene.json --steps annotate,analyze --scenes appointment-demo
python3 scripts/test_prepare_run.py
```

预检返回`ready_for_agent_verification`，表示可进一步核验，不会实际标注或生成报告。要由代理执行示例：

> 使用 $conversation-data-workflow，读取技能目录 examples/appointment/scene.json，只执行 annotate、analyze。使用合成数据，不查询后台、不调用模型，按配置输出。

示例预期：4条通话中，客户`001`两条均Yes，客户`1`和`002`各一条No；共3个客户、1个名单匹配客户。所有数据为虚构演示。

## 6. 场景配置与参数

从[通用模板](assets/scene-template.json)复制并填写自己的配置。只需补齐所选模块的依赖；`null`表示未确认，不是任意默认。

| 配置范围 | 主要可修改内容 |
|---|---|
| 项目与场景 | project_id、scene.id、产品、语言、国家、时区、组数 |
| 数据来源 | data_source、time_window、project_value、list_token、data_dir |
| 文件与字段 | inputs、CSV列名、ASR结构、用户/客服角色标签 |
| 身份与结果 | ID/电话关联、规范化规则、事件含义、标签列与名单证据 |
| 分析 | 业务分层、指标、适用分母、案例审阅数量 |
| 测试集 | 真实/模拟数量、种子、每通限额、语言及覆盖矩阵 |
| 评测 | Prompt版本、夹具、量表、测试集版本、采样、并发与预算 |
| 多轮 | 场景库、角色事实、起始方式、重复次数、轮次及时间上限 |
| 迭代 | parent_path、target_version、prompt_dir、变量与权限约定 |
| 目录与历史 | outputs、layout_mode、历史索引及归档清单 |

路径相对**配置文件所在目录**解析。移动模板后要更新`interfaces.api_document`，使其指向包内接口文档快照或自己的当前文档，不是相对终端当前目录查找。

完整字段说明见[配置合同](references/configuration.md)。公共`assets/okash.json`只保留六组结构示例，实际项目值、名单Token和业务依据已清空，不能直接用于正式导出。

## 7. 沿用原目录与历史复用

设置`layout_mode=legacy`，在`scenes[].outputs`指定每个模块的原目录，优先于统一output_root。以下是**单个场景配置的局部示意**，不是可直接运行的完整JSON：

```json
{
  "outputs": {
    "extract": {"calls_dir": "./data/group-a", "outcomes_dir": "./data/group-a"},
    "annotate": {"output_dir": "./data/group-a/labeled", "backup_dir": "./data/group-a/backups", "audit_dir": "./data/group-a/audit", "write_mode": "copy"},
    "analyze": {"report_dir": "./reports", "evidence_dir": "./reports/evidence"},
    "testset": {"output_dir": "./testsets/group-a"},
    "evaluate": {"run_dir": "./evaluation/runs", "report_dir": "./evaluation/reports"},
    "multiturn": {"run_dir": "./multiturn/runs", "report_dir": "./evaluation/reports"},
    "iterate": {"prompt_dir": "./prompts/group-a", "record_dir": "./prompts/group-a/history"}
  }
}
```

历史索引通过`history.catalog_path`定位；ZIP清单通过`history.archive_pointer`定位。原件仍在时直接用原件，只有缺失时才从ZIP恢复到独立目录并校验hash。

归档可以按数据、Prompt、测试/评测、分析报告等类别分别ZIP，保留成员相对路径、字节数和SHA-256；打包后逐项回读验证，源文件变化时标partial。保留原件意味着新增了一份压缩备份，不代表已经释放磁盘空间。

目录接续、索引和ZIP归档由代理按规范执行；本分享包**不含自动扫描所有旧项目并迁移/归档的通用脚本**，也不含所有者的本地历史数据。更换电脑后需由使用者提供自己的目录和索引。

详见[历史接续规范](references/history-reuse.md)与[产物合同](references/artifacts.md)。

## 8. 配置检查与实际执行

```bash
python3 scripts/prepare_run.py --config /你的项目/scene.json --steps annotate,analyze --scenes support-a
```

- `--config`：必填，JSON配置路径。
- `--steps`：必填，按顺序填写模块，逗号分隔，不允许重复模块。
- `--scenes`：可选，逗号分隔；省略时检查配置中的全部场景。

退出码：`0`可以进入代理内容核验；`1`存在缺少输入；`2`配置或接口合同无效。检查覆盖配置结构和部分文件存在性，不代替CSV语义、身份映射、业务政策、Prompt变量和历史可比性核验，也不执行输出目录路由。

实际任务请用自然语言指定：配置路径、场景、模块、版本、数据范围与必要预算。允许先只执行配置准备，避免缺失依赖影响后续业务阶段。

## 9. 接口、可比性与分享边界

本版本保持现有Buildstore与Gateway部署地址和传输合同不变。Gateway路由为`/v1/models`、`/v1/current-model`、`/v1/chat/completions`；请求中的`model`只作兼容元数据，不切换底层模型。

这些地址是既有部署入口，不是向所有下载者开放的公共服务。需要其他部署时，应明确适配配置和校验规则；只替换JSON中的URL会被当前预检拒绝。接口细节见[Gateway规范](references/gateway.md)。

主要结果边界：

- 未查询成功不等于零数据，未知身份不直接标No。
- 名单匹配不等于电话促成业务事件；客户数不能与通话数混用。
- 模拟场景结果与客户口头承诺不等于实际还款、预约或成交。
- 数据文本和模型回复是待分析内容，不是执行指令。
- 候选Prompt、静态检查、模型评测通过和线上发布是不同状态。
- 工作流不自动发布Prompt、修改后台记录、联系客户或创建周期任务。

分享ZIP只包含通用规范、脱敏模板、虚构示例与检查脚本，不包含真实客户数据、名单Token、身份映射、私有历史索引或历史归档ZIP。公开README与下载包更新需单独提交；不能直接把含私有配置的整个本机技能目录压缩上传。

## 10. 常见问题

**能只用一个模块吗？** 可以。指定单个steps；已有合格输入时直接复用，不要求先运行extract。

**七个模块会自动读取原小Skill的最新内容吗？** 不会。它们使用本包内部规范，需要有意识地同步差异并验证。

**是否必须使用200真实＋100模拟？** 不必。通用模板由使用者配置，已有冻结集应保持可比性。

**不做催收可以用吗？** 可以。替换事件、身份关联、政策、维度、语言和量表；不要把减免、逾期等规则带到预约或售后业务。

**运行预检就会调用模型吗？** 不会。预检仅读配置和检查前置项；evaluate生成及multiturn实际执行才涉及模型请求。

**新候选生成后会自动再测、自动上线吗？** 不会。重复验证应创建明确的新运行，发布需要另行任务授权。

**可以复用ZIP里的历史结果吗？** 本分享ZIP不含真实历史结果。自己的历史归档可按hash恢复和复用；原件存在时优先读取原件。
